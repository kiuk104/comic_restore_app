# 이북 모바일 뷰어 ↔ 킨들 이어읽기 비교 및 개선안

2026-07-26 · 대상: `edit_ui.html`(뷰어 UI) + `ebook_gas_sync.gs`(state op)

## 1. 현재 구현이 "정확하지 않게" 느껴지는 이유 (코드 분석)

현재 위치 저장·복원 체인은 다음과 같다.

- **저장 단위 = 문단 인덱스(정수)**. `curIdx()`가 "헤더 밑변(+4px) 아래로 걸쳐 있는 첫 문단"을 찾고, 그 정수 인덱스만 `_bmkSet(i)`로 저장한다(localStorage + CLOUD `op:'state'` / SRV `/api/marks`). 문단 안에서 어디까지 읽었는지는 버려진다.
- **복원 = 문단 첫 줄을 헤더 밑에 정렬**. `_bmGo()`/`_restGo()`가 해당 문단의 top을 헤더 밑변에 맞춘다.

여기서 체감 오차가 세 겹으로 쌓인다.

1. **문단 내 위치 소실 (최대 한 문단만큼 되감김)** — 저장 시점에 화면 맨 위 문단은 보통 "거의 다 읽고 끝자락만 보이는" 상태다. 그런데 복원은 그 문단의 **처음**으로 돌아간다. 긴 문단(폰에서 여러 화면 분량)일수록 "읽던 데가 아닌데" 느낌이 커진다. 독일어 원문 병기(rdo)까지 켜져 있으면 문단 하나가 더 길어져 오차도 커진다.
2. **닫기 직전 스크롤 분실** — 저장은 scroll 700ms 디바운스 + `curIdx` 변화 시에만, 네트워크 전송은 추가 1200ms 디바운스다. PWA를 홈으로 내리거나 셸에서 ⌂로 나가면 마지막 1~2초의 스크롤이 전송되지 않은 채 죽을 수 있다(종료 시 flush 없음). 또 열고 나서 2.5초(`performance.now()<2500`)는 저장 자체를 무시하므로, 열자마자 읽고 바로 닫는 패턴에서도 위치가 밀린다.
3. **복원 후 이중 점프 / 충돌 처리** — 로컬 값으로 즉시 복원한 뒤 클라우드 값이 "다르면" 무조건 클라우드로 재점프한다. GAS는 `{pos, ts}`로 timestamp를 이미 저장하고 있지만 비교에는 쓰지 않아서, 오프라인이던 기기가 뒤늦게 옛 위치를 올리면 되감기는 시나리오도 가능하다.

## 2. 킨들은 어떻게 하나

- **Location = 콘텐츠 기준 앵커**. 킨들의 location은 책 파일의 약 128바이트 단위 오프셋으로, 화면 크기·폰트 크기·기기와 무관하게 **콘텐츠 자체에 박힌 좌표**다. 문단보다 훨씬 잘다(대략 한두 문장 이하). 내부적으로는 location보다 더 정밀한 바이트 단위 위치를 저장하기 때문에 "화면 첫 단어" 수준으로 복원된다.
- **Whispersync = 즉시 + 이벤트 기반 동기화**. 책을 펴고 닫을 때, 기기가 슬립에 들어갈 때 위치를 서버로 바로 보낸다. 디바운스에 기대지 않으므로 "닫기 직전 위치"가 유실되지 않는다.
- **last position과 furthest page read를 분리 저장**. 뒤로 넘겨 찾아봐도 "가장 멀리 읽은 지점"은 따로 유지되고, 기기 간 위치가 다르면 타임스탬프 기준으로 "다른 기기에서 여기까지 읽음 — 이동할까요?"를 묻는다.

정리하면 격차의 본질은 세 가지다: **① 앵커의 해상도(문단 vs 콘텐츠 오프셋), ② 저장 타이밍(디바운스 vs 이벤트 flush), ③ 충돌 규칙(클라우드 무조건 우선 vs 타임스탬프)**.

## 3. 개선 제안 (비용 낮은 순, 최적화 관점)

### 제안 A. 종료 시 즉시 flush — 비용 최소, 체감 효과 큼

`visibilitychange`(hidden)·`pagehide`에서 디바운스 타이머를 기다리지 않고 현재 위치를 즉시 전송.

- CLOUD: `navigator.sendBeacon(GURL, JSON문자열)` — GAS `doPost`는 `e.postData.contents`를 `JSON.parse`하므로 text/plain beacon으로 그대로 동작하고, beacon은 페이지가 죽어도 브라우저가 전송을 보장한다. (헤더 ⌂ 클릭 시 `cloudSend()` 하는 것과 같은 발상을 OS 레벨 이탈에도 적용하는 것.)
- SRV: `fetch(..., {keepalive:true})`.
- 함께: 초기 2500ms 무시 창을 시간이 아니라 **복원 중 플래그**(`_restTarget` 활성 여부)로 대체 — 이미 있는 `_restStop`/`_restTarget` 인프라로 충분하다.

### 제안 B. 문단 내 오프셋 저장 — 킨들 location과 같은 원리

저장 시 판정선 지점의 **글자 오프셋**을 함께 기록한다. 구현 재료가 이미 코드에 다 있다:

- 저장: `document.caretRangeFromPoint(x, 헤더밑변)` → 텍스트 노드+offset → **기존 `_hoff(rd, node, pos)`** 로 문단 내 글자 오프셋 n. 저장 형태 `{pos:i, off:n}`.
- 복원: `_bmGo`에서 rdFill 후 TreeWalker(기존 `_hiWrap`과 동일 순회)로 off 지점에 Range를 만들어 `getBoundingClientRect().top`을 헤더 밑변에 정렬.
- 동기화: GAS는 `e.state = {pos:q.pos, ts:...}` 한 줄을 `{pos:q.pos, off:q.off||0, ts:...}`로 확장(재배포 1회). 구버전 GAS/클라이언트는 off를 무시하고 지금처럼 문단 단위로 동작 — **하위 호환 자동**.

글자 오프셋은 콘텐츠 앵커라서 **PC(큰 화면)↔폰(작은 화면)처럼 레이아웃이 다른 기기 간에도 정확**하다. 이게 픽셀 비율 방식(대안: `pos = i + 지나간높이/문단높이` 소수점 저장 — 코드 5줄이면 되지만 폰트 크기 바뀌면 어긋남)보다 이 프로젝트에 맞는 이유다. 빠른 개선이 필요하면 소수점 방식을 1단계로 넣고 나중에 오프셋으로 승격해도 된다(둘 다 pos 숫자 하나라 프로토콜 변경 없음).

### 제안 C. 저장 판정과 이중 점프 완화

- 저장 트리거를 "curIdx 변화"에서 "**i 변화 또는 off가 임계(예: 40자) 이상 변화**"로. 긴 문단 안에서 읽는 동안에도 위치가 갱신된다. 전송량 증가는 디바운스(1200ms)가 이미 흡수.
- 복원 후 클라우드 보정은 "**같은 문단이고 off 차이가 작으면 재점프 생략**" — 미세한 이중 점프가 사라진다.

### 제안 D. 타임스탬프 충돌 해결

로컬에도 `{pos, off, ts}`로 저장하고, 클라우드 `state.ts`(이미 저장되고 있음)와 비교해 **최신 쪽 채택**. "클라우드 무조건 우선"으로 인한 되감김 시나리오 제거. Whispersync의 규칙과 동일.

### 제안 E. (선택) furthest 분리 — 서재 진행률 후퇴 방지

현재 셸 서재의 "#N까지 검수 (%)"는 마지막 위치 `pos` 기준이라, 북마크로 앞부분에 다녀오거나 검색으로 점프하면 진행률이 후퇴한다. 킨들처럼 `far = max(far, pos)`를 state에 한 필드 추가하고 서재 진행률만 far 기준으로 바꾸면 해결. (list op의 `info` 계산 한 줄 변경.)

## 4. 성능 노트

추가 비용은 사실상 0에 가깝다. `caretRangeFromPoint`+`_hoff`는 스크롤 프레임이 아니라 **700ms 디바운스된 저장 시점에만** 1회 실행되고(수천 자 문단 TreeWalker 순회도 <1ms 수준), 복원 시 Range rect 계산 1회뿐이다. 네트워크 왕복도 기존 `op:'state'`/`/api/marks`에 필드만 얹으므로 증가 없음. sendBeacon은 오히려 이탈 시 fetch 재시도성 문제를 줄인다. 기존의 8프레임 settle + fonts.ready 재보정 루프는 그대로 두면 오프셋 기준 정렬에도 똑같이 작동한다.

## 5. 적용 순서 권장

1. **A(flush) + C(이중 점프 완화)** — GAS 재배포 불필요, PC 재시작+☁업로드만으로 반영. 체감 개선의 절반 이상.
2. **B(오프셋 앵커)** — edit_ui.html + GAS state 확장(재배포 1회).
3. **D(ts 충돌)** — B와 같은 배포에 묶기.
4. **E(furthest)** — 여유 있을 때.
