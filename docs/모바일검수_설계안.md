## 1. 목표와 확정 사항

이북 번역 검수는 시간이 오래 걸리므로 **PC가 꺼진 상태에서도 폰으로** 이어서 한다.

- 모바일 범위: **원문(src)·번역(text) 텍스트 수정만** — 재전사·재번역·재생성은 PC 전용
- 방식: **동기화 서버를 기존 계정 서비스에 둔다** — 주안은 Google Apps Script(+Drive), 대안은 GitHub 비공개 저장소(§7)
- 폰은 **URL 북마크 하나로 접속** (파일 나르기 없음), 수정분은 자동 업로드

## 2. 전체 파이프라인

```
[PC]  번역 실행 → [☁ 업로드] (또는 실행 완료 시 자동)
        └→ GAS 웹앱에 edit.html(CLOUD 모드, 데이터+fp 내장) 업로드 → Drive 저장
                                    │
[폰]  GAS 배포 URL 열기 ──────────────┘  항상 최신 스냅샷이 뜸 (https)
        └→ 검수·수정 → 수정분 자동 POST (debounce) → Drive의 edits.json 큐에 병합
        └→ 오프라인 순간엔 localStorage 대기열 → 재접속 시 재전송
                                    │
[PC]  [☁ 모바일 수정 반영] ──────────┘  edits 큐 다운로드
        └→ fp 검증 → _edit_save() 반영 → 큐 비움 → 새 스냅샷 자동 업로드
        └→ 필요 문단만 🌐 재번역 → [📖 TXT/EPUB 재생성]
```

v1 대비 이점: 파일 수동 전달 소멸, Drive 미리보기 JS 미실행 문제 소멸(정식 https 서빙),
localStorage가 안정적인 https origin에서 동작(iOS 포함), 폰이 열 때마다 최신 스냅샷이라
fp 불일치가 구조적으로 희귀해짐, 명시적 [내보내기] 없이 수정 즉시 저장.

## 3. 서버 — Google Apps Script (신규 `ebook_gas_sync.gs`, ~120줄)

GAS는 **멍청한 릴레이**로 유지한다. UI·데이터 로직은 전부 파이썬 쪽 단일 소스.

- 저장소: 본인 Drive 폴더 `ebook_review_sync/` — 책별로 `{title}.html`(스냅샷 페이지), `{title}_edits.json`(수정 큐)
  ※ 사용자의 독서 소스 텍스트(eBook_viewer가 읽는 txt/md)도 **이미 Google Drive에 있음**
  (2026-07-18 확인) — Drive가 라이브러리 전체의 서고. 검수 데이터·카탈로그·완성본을 같은 Drive
  체계에 두면 일원화되며, ebook_translate 완성본(TXT/EPUB)의 Drive 자동 업로드가 자연스러운
  다음 연결 고리(뷰어가 바로 읽음). 폴더 구조는 구현 시 기존 소스 폴더 배치를 보고 결정.
- `doGet`:
  - `?book={title}` → 저장된 HTML 그대로 서빙 (HtmlService)
  - `?api=edits&book=…&key=…` → 수정 큐 JSON 반환 (PC 반영용)
- `doPost` (body JSON, `key` 필수):
  - `op:"upload"` → HTML 저장(스냅샷 교체) + 수정 큐 초기화 여부 옵션
  - `op:"edits"` → `{i:{src?,text?,ts}}` 맵을 기존 큐에 병합 (같은 i는 last-write-wins)
  - `op:"clear"` → 반영 완료 후 큐 비움 (반영한 fp 명시 — 다른 fp면 거절)
- 인증: 배포는 "링크가 있는 모든 사용자" + **자체 secret key**를 모든 요청에서 검사.
  폰은 최초 1회 key 입력 → localStorage 저장. PC는 ebook_config.json의 `gas_url`/`gas_key`.
- 배포: script.google.com에 ebook_gas_sync.gs 붙여넣기 → 웹앱 배포(나로 실행) → exec URL 복사.
  코드 수정 시 재배포 필요(잦지 않음 — 릴레이라 로직이 안 바뀜). 1인 사용량은 무료 할당량으로 충분.

### 뷰어 확장 여지 (로드맵 연계 — 이번 구현 범위 아님, 구조만 대비)

사용자 로드맵: 개인 디지털 라이브러리 시스템. 기존 뷰어 앱에 없는 기능 —
① 번역문↔원문 대조 보기 ② 읽던 중 오타 즉시 수정 ③ 독서 목록·카테고리 개인화 —
때문에 별도 뷰어가 필요하며, **이 검수 페이지가 그 뷰어의 전신**이 된다:

- ①은 book.json이 이미 문단별 src+번역 쌍 → 데이터 추가 없이 표시 모드 문제
- ②는 CLOUD 모드 자동 업로드 큐 그 자체 — 읽기 모드(👁 미리보기 렌더러)↔편집 모드 토글로 발전
- ③은 Drive에 카탈로그 JSON(목록·카테고리·읽던 위치) + `?list` 서재 페이지로 발전

이번 구현에서 지켜둘 것: 책별 파일 구조(`{title}.html`/`{title}_edits.json`) 유지,
doGet 라우팅을 쿼리 파라미터 기반으로(나중에 `?list` 추가가 자연스럽게),
읽던 위치(문단 인덱스)를 edits와 같은 채널로 올릴 수 있는 op 하나 여유(`op:"state"` 예약).

**기존 뷰어 프로젝트 확인 (2026-07-18 추가)**: `E:\Coding\eBook_viewer` (v0.3.0, Electron 주력
+웹 버전, 2026-02까지 개발). 편집 모드(contentEditable·실행취소·자동저장·localStorage 임시저장),
읽기 위치·진행률·북마크·하이라이트·테마/폰트 개인화·히스토리·백업, **Google Drive OAuth+Picker**까지
이미 구현 — 로드맵 기능 중 ①대조 보기 ②카테고리 서재 ③파이프라인 왕복만 없음.

→ 통합 방침: **edits.json 스키마(§6)를 뷰어↔파이프라인 공용 계약으로** 삼는다. 대조 보기는
ebook_translate가 book.json(src+번역 쌍)을 뷰어용으로 내보내면 데이터 충족.

→ **구현 세션 분기점**: 뷰어가 Drive OAuth를 이미 해결했으므로, 동기화를 ⓐ GAS 릴레이(이 문서 §3,
검수 페이지 즉시 사용 가능) ⓑ 뷰어가 Drive API로 book/edits.json 직접 읽고 쓰기(뷰어를 공개 호스팅,
데이터는 본인 Drive — GAS 불필요, 단 OAuth origin 등록·뷰어 개조 필요) 중 선택하거나 병행
(ⓐ로 검수 먼저, ⓑ로 뷰어 통합). 어느 쪽이든 edits.json·fp 게이트·_edit_save 경로는 동일.
참고: 뷰어의 Gemini 모델명은 낡음(1.5-flash-002) — AI 변환 기능은 통합 시 손봐야 함.

### 구현 검증 포인트 (설계 시점 미확정 — 구현 때 실기기 확인)

- HtmlService 서빙 페이지에서 `google.script.run`으로 doPost 없이 서버 함수 직접 호출 가능
  → 가능하면 CORS 걱정 자체가 없음 (1순위). 안 되면 exec URL로 `fetch` POST
  (Content-Type `text/plain`로 preflight 회피 — GAS 표준 우회 패턴) (2순위).
- 1~2MB급 HTML(긴 책)을 HtmlService로 서빙할 때 지연 허용 범위인지.
- IFRAME 샌드박스에서 localStorage 동작 확인 (동일 origin 공유 여부).

## 4. PC 측 — `ebook_translate_web.py`

Api 추가 (~80줄) + 버튼 2개:

- `cloud_push()` = [☁ 업로드]: `write_edit_html()`(CLOUD 플래그) 결과를 doPost `op:"upload"`로 전송.
  옵션: 번역 실행 완료 시 자동 업로드 체크박스 (`ebook_config.json`).
- `cloud_pull()` = [☁ 모바일 수정 반영]:
  1. `?api=edits`로 큐 다운로드
  2. **fp 게이트**: 큐의 fp가 현재 book.json의 fp와 일치할 때만 반영 (재전사 등으로 문단
     구조가 바뀐 경우 차단 + 사유 로그 — 인덱스 시프트 사고 방지)
  3. `_edit_save(out, edits, log)` 그대로 호출 — 원자적 저장·src.txt 동기화·로그 공짜
  4. `op:"clear"` → 새 스냅샷 자동 `cloud_push()` (폰이 다음에 열면 반영본이 보임)
  5. `is_busy` 규칙 재사용: 번역 실행 중이면 거절 (xlat.json 쓰기 경합 방지)
- 네트워크는 `urllib`로 충분 (GAS는 302 리다이렉트 후 응답 — follow 기본).
- 설정 키: `gas_url`, `gas_key`, `gas_auto_push` — Tk와 공유하는 `_SAVE_KEYS`에 포함해 양쪽 호환.

## 5. 폰 측 — `EDIT_HTML` CLOUD 모드 (~100줄 추가)

기존 `SRV` 분기에 셋째 모드 추가: `CLOUD = __DATA__`에 `gas:true` 플래그.

- 숨김: 재전사·재번역·원본보기·TXT/EPUB 재생성 (기존 `!SRV` 처리 재사용)
- 유지: 👁 미리보기(순수 JS), 필터(전체/실패만/수정됨만), § 제목 토글
- 저장 동작: `mark()` 후 debounce(~2초) 자동 POST — 헤더에 상태 표시
  `☁ 저장됨 / ⏳ 대기 N건 / ⚠ 오프라인(재접속 시 전송)`
- 안전망: 미전송분 localStorage 보관(`ebookEdits:{title}:{fp}`) → 페이지 재진입 시 재전송,
  `beforeunload` 경고. 전송 성공분만 대기열에서 제거.
- 최초 1회 key 입력 프롬프트 → localStorage. key 오류 시 재입력 유도.
- 터치 보정: 버튼 최소 높이 ~36px, textarea 폰트 16px(iOS 자동 줌 방지).
- 스냅샷 신선도: 페이지에 업로드 시각 표시. (폰이 열어둔 채 PC가 새 스냅샷을 올린 경우를
  위해, POST 응답에 서버 측 fp를 실어 불일치면 "새 버전 있음 — 새로고침" 배너.)

## 6. 데이터 형식

수정 큐 `{title}_edits.json` (서버 보관, PC가 내려받는 것):

```json
{
  "v": 1,
  "fp": 123456789,          // 폰이 편집한 스냅샷의 지문 (crc32 전체 src 결합)
  "count": 842,
  "edits": { "12": {"src": "…", "ts": 1789000000},
             "40": {"text": "…", "ts": 1789000123} }
}
```

PC 반영 시 `edits` 맵 → `[{i,src?,text?}]` 배열로 변환 = 기존 `/api/save` 페이로드와 동일
→ 서버 모드/CLOUD 모드가 같은 `_edit_save()` 경로로 수렴.

## 7. 대안: GitHub 비공개 저장소 (채택 보류)

서버 코드 0줄 — PC가 Contents API로 snapshot 푸시, 폰 페이지가 API로 직접 읽고 씀(커밋 이력 공짜).
보류 이유: ① 폰에 fine-grained PAT 보관 필요 ② 데이터 내장 페이지를 호스팅할 곳이 마땅치 않음
(무료 Pages는 공개 저장소만 → 공개 셸+비공개 데이터 분리 필요) ③ Contents API 파일당 ~1MB 제한으로
큰 책은 분할 저장 로직 추가. GAS 방식이 막히면 이쪽으로 전환 — 데이터 형식(§6)은 그대로 재사용 가능.

## 8. 폴백: 오프라인 왕복 (v1안)

네트워크 없는 환경(비행기 등)용으로 v1의 [📤 내보내기]/[📥 이어서](edits.json 수동 전달)를
CLOUD 모드에도 남겨둔다 — 같은 edits 형식이므로 PC [☁ 모바일 수정 반영]에 파일 선택 폴백만 추가.

## 9. 운영 규칙

- **폰 수정분 먼저 반영, 그다음 재전사·재실행** (fp 불일치 시 차단되지만, 차단되면 폰 수정분을
  살릴 수 없으므로 습관이 중요)
- 같은 문단을 폰·PC 양쪽에서 고치면 나중에 반영한 쪽이 이김 (1인 작업 — 병합 UI 없음)
- 책 원문 전체가 본인 Google 계정(Drive)에 저장됨 — 개인 비공개 용도로 문제없으나 인지할 것.
  스캔 이미지가 아닌 텍스트만 올라감.

## 10. 구현 범위 (다음 세션)

| 파일 | 변경 |
|---|---|

검증: `py_compile` + `node --check` + 헤드리스(모의 GAS 서버로 push→edits 병합→pull→fp 차단 케이스)
+ 실기기 체크리스트(§3 검증 포인트: google.script.run, 대용량 서빙, localStorage / Android·iOS 각 1회).
